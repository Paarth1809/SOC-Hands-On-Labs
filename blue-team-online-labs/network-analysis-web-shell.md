### Scenario

The SOC received an alert in their SIEM for ‘Local to Local Port Scanning’ where an internal private IP began scanning another internal system. Can you investigate and determine if this activity is malicious or not? You have been provided a PCAP, investigate using any tools you wish.

### Difficulty

* Easy

### Requirements

* Winodws 10
* Wireshark

I worked through the PCAP by checking the network protocols, TCP connections, HTTP requests, and\
the commands sent through the web shell. The screenshots below show the main steps I used to\
follow the activity from reconnaissance to the reverse shell.

### Initial Findings

I started by looking at the traffic and identifying the internal hosts involved. The investigation\
showed activity from the internal system toward the web server, followed by reconnaissance, a file\
upload, web-shell execution, and finally a reverse shell.

### Investigation

#### Port Scan Activity

I checked the TCP traffic to identify the systems communicating during the scan. The traffic shows the\
internal hosts involved and helped me focus on the connection to the web server.

<figure><img src="../.gitbook/assets/image (45).png" alt=""><figcaption></figcaption></figure>

Next, I reviewed the connection list in Wireshark to see which ports were being contacted. This helped\
confirm that the activity was not just a single normal connection.

<figure><img src="../.gitbook/assets/image (46).png" alt=""><figcaption></figcaption></figure>

The packet view shows the TCP SYN traffic used during the scan. From the investigation, the scanned\
range was identified as ports 1–1024.

<figure><img src="../.gitbook/assets/image (47).png" alt=""><figcaption></figcaption></figure>

#### Gobuster Reconnaissance

I filtered the HTTP traffic and checked the request headers. The User-Agent identifies Gobuster 3.0.1,\
showing that directory/file enumeration was being performed against the web server.

<figure><img src="../.gitbook/assets/image (48).png" alt=""><figcaption></figcaption></figure>

I then followed the related HTTP traffic to see the requests generated by Gobuster. The repeated\
requests and responses confirmed the reconnaissance activity.

<figure><img src="../.gitbook/assets/image (49).png" alt=""><figcaption></figcaption></figure>

The request/response details gave another view of the same enumeration activity. This was the first\
clear indication that the traffic was related to web reconnaissance.

<figure><img src="../.gitbook/assets/image (50).png" alt=""><figcaption></figcaption></figure>

#### Gobuster Server Responses

I followed the HTTP stream to inspect how the server responded to the Gobuster requests. The\
User-Agent is visible in the request, while the server response confirms the web server being tested.

<figure><img src="../.gitbook/assets/image (51).png" alt=""><figcaption></figcaption></figure>

The second HTTP stream view shows the server returning the requested page/error content. This helped\
confirm that the traffic was generated by automated web enumeration.

<figure><img src="../.gitbook/assets/image (52).png" alt=""><figcaption></figcaption></figure>

#### SQLmap Activity and File Upload

I next checked the POST requests and noticed the User-Agent sqlmap/1.4.7. This showed that sqlmap\
was being used for further testing of the web application.

<figure><img src="../.gitbook/assets/image (53).png" alt=""><figcaption></figcaption></figure>

The HTTP response also showed activity around the upload area. I used this traffic to trace how the\
attacker moved from reconnaissance toward uploading a file.

<figure><img src="../.gitbook/assets/image (54).png" alt=""><figcaption></figcaption></figure>

#### Decoding the SQL Request

The POST request contained URL-encoded data, so I decoded it to make the parameters easier to read.\
The decoded request exposed the SQL payload and the command-execution portion used during the\
attack.

<figure><img src="../.gitbook/assets/image (55).png" alt=""><figcaption></figcaption></figure>

After decoding the request, I could see the reference to the database information and the command\
execution payload. The uploaded web-shell file was later identified as dbfunctions.php.

<figure><img src="../.gitbook/assets/image (56).png" alt=""><figcaption></figcaption></figure>

#### Web Shell Upload

I followed the upload request and checked the multipart form data. The uploaded PHP file was named\
dbfunctions.php, confirming the web shell was placed on the server.

<figure><img src="../.gitbook/assets/image (57).png" alt=""><figcaption></figcaption></figure>

I then inspected the GET request to the uploaded file. The request contained the cmd parameter, which\
is the parameter used by the web shell to execute commands on the server.

<figure><img src="../.gitbook/assets/image (58).png" alt=""><figcaption></figcaption></figure>

#### Command Execution and Reverse Shell

I decoded the command parameter to see what was being executed. The decoded value showed a\
Python-based reverse-shell command connecting back to the attacking host on TCP port 4422.

<figure><img src="../.gitbook/assets/image (59).png" alt=""><figcaption></figcaption></figure>

Finally, I followed the resulting shell activity. The terminal output shows commands such as whoami, cd,\
and ls being executed as the www-data user.

<figure><img src="../.gitbook/assets/image (60).png" alt=""><figcaption></figcaption></figure>

#### Final Evidence

The final terminal output shows the attacker interacting with the compromised web server. I used\
this evidence together with the packet analysis to answer the lab questions.

<figure><img src="../.gitbook/assets/image (61).png" alt=""><figcaption></figcaption></figure>

### Answering the Questions

1. What is the IP responsible for conducting the port scan activity?
   1. 10.251.96.5
2. What is the port range scanned by the suspicious host?
   1. 1-1024
3. What is the type of port scan conducted?
   1. TCP SYN
4. Two more tools were used to perform reconnaissance against open ports, what were they?
   1. gobuster 3.0.1, sqlmap 1.4.7
5. What is the name of the php file through which the attacker uploaded a web shell?
   1. editprofile.php
6. What is the name of the web shell that the attacker uploaded?
   1. dbfunctions.php
7. What is the parameter used in the web shell for executing commands?
   1. cmd
8. What is the first command executed by the attacker?
   1. id
9. What is the type of shell connection the attacker obtains through command execution?
   1. reverse shell
10. What is the port he uses for the shell connection?
    1. 4422

### Conclusion

The investigation shows a progression from internal port scanning to web reconnaissance, SQLmap\
activity, web-shell upload, command execution, and a reverse-shell connection. Based on the\
evidence collected in the PCAP, the activity is malicious.
